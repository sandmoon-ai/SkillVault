# Krug Usability Review（点石成金）

审 Web/App 是否「别让我思考」。目标：找出迫使用户停下来猜的点，并给出可改方案。

规则来源：Steve Krug《Don't Make Me Think, Revisited》/《点石成金》。只输出可验证问题与改法，不写空泛 UX 口号。

## 何时使用

- 审页面、落地页、后台、移动 App 截图/原型
- 用户说难用、找不到、要猜、导航乱、「别让我思考」
- 需要 Trunk Test 或低成本可用性体检

深度改文案结构 → `krug-scan`；重做导航/首页 → `krug-navigation`；组织测试 → `krug-usability-test`。

## 工作流

```
Review Progress:
- [ ] 1. 定场景：任务、设备、新访客 vs 回访
- [ ] 2. 抓「思考瞬间」（第一定律）
- [ ] 3. 跑 Trunk Test
- [ ] 4. 扫描与噪声
- [ ] 5. 选择是否无脑
- [ ] 6. 礼貌账户 / 移动要点 / 无障碍底线
- [ ] 7. 按严重度输出，只优先最伤任务的问题
```

## 1. 场景

写清：

- **用户要完成的任务**（1 句）
- **设备**：桌面 / 手机 / 两者
- **身份**：首次访问是否成立

没有真实任务时，自拟 1–2 个核心任务再审。

## 2. 第一定律：别让我思考

逐屏找「思考瞬间」——用户必须停下来解读、猜、或犹豫：

| 症状 | 例子 |
|------|------|
| 命名含糊 | 「解决方案」「平台」「更多」不知所指 |
| 可点性不明 | 文字/卡片/图标像装饰又像链接 |
| 创意压过清晰 | 导航双关语、谜语式入口 |
| 术语门槛 | 行业黑话当导航标签 |
| 同页多种叫法 | 同一功能「账户/个人中心/我的」混用 |

判定：

- **不言自明（self-evident）** 最好
- 做不到则至少 **自解释（self-explanatory）**——短标签/一句说明即可懂
- 需要说明书才能点 → Critical

## 3. Trunk Test（树干测试）

想象被蒙眼丢到站内任意页，睁眼后应能立刻回答：

1. **这是什么网站/产品？**（站点 ID / Logo）
2. **我在哪一页？**（页面名称够显眼，且与点进来的链接一致）
3. **主要栏目有哪些？**（全局导航）
4. **此页有哪些下级选项？**（局部导航）
5. **我在整体结构的哪里？**（当前位置高亮 / 面包屑）
6. **怎么搜索？**（若站点需要搜索；控件应叫「搜索/Search」，别玩花样）

任一题答不出或要猜 → 记为导航/定位问题（可转交 `krug-navigation` 细改）。

## 4. 扫描与噪声

用户扫读，不精读。检查：

- 视觉层级是否表达重要性、归属、同类？
- 重要内容是否像广告牌一样跳进视线？
- 噪声：抢戏动画、并列强调过多、伪广告模块、装饰压过任务
- 正文是否利于扫描：短段、标题、列表、关键词可见

（细则改稿用 `krug-scan`。）

## 5. 选择是否「无脑」

第二定律精神：**点击次数多少不如每次选择是否轻松**。

- 每个分叉是否像「动物 / 植物 / 矿物」一样互斥清晰？
- 是否迫使用户比较难懂的抽象类别？
- 是否存在假选择（看起来不同、实际不知区别）？

## 6. 礼貌、移动、无障碍（底线）

**礼貌（善意账户）**——别无谓消耗耐心：

- 隐藏的成本、障眼法式注册墙、找不回的关键操作
- 错误信息指责用户、不说怎么修
- 夸大承诺后找不到出口

**移动**：

- 首屏是否露出核心任务？
- 触控目标是否够大、间距是否防误触？
- 是否把桌面信息密度硬塞进小屏？
- 拇指可达的主操作是否合理？

**无障碍底线**（不做完整 a11y 审计，只抓明显债）：

- 仅靠颜色传达状态
- 无文本等价的关键图标按钮
- 对比过低的字
- 焦点/键盘路径明显断裂（若可观察）

## 输出格式

```markdown
# Krug Usability Review

**任务**: …
**设备**: …
**总判**: [1–2 句：最大「思考税」是什么]

## Trunk Test
| 问题 | 结果 | 备注 |
|------|------|------|
| 什么站？ | ✅/❌ | … |
| 哪一页？ | | |
| 主栏目？ | | |
| 本页选项？ | | |
| 我在哪？ | | |
| 怎么搜？ | | |

## 问题清单

### 🔴 Critical（阻碍任务）
1. **[现象]** → 违反：思考瞬间 / Trunk / …
   - 用户会怎样猜错或放弃
   - 改法：…

### 🟡 Should fix
…

### 🟢 Nice to have
…

## 建议改稿顺序
1. 先修阻碍主任务的思考瞬间
2. 再修定位（Trunk）
3. 再收噪声与文案
```

规则：

- 每条问题要能指出「用户卡在哪一步」
- 先严重、后完美；一次报告别变成 50 条品味清单
- 有文件/URL/截图则指到具体区域；没有则给风险清单并索要样本

## 反模式（审稿时自己也避免）

- 用「不够现代/不够高级」代替可用性证据
- 把品牌审美争议当成可用性缺陷
- 建议大重构却不指出当前任务失败点
- 忽略移动单独套桌面结论

## 边界

- 不裁决商业模式对错，只审完成任务的摩擦
- 与 `tsutawaru-*`：视觉排版清晰度可叠用；本 skill 侧重认知与导航摩擦
- 需要改扫描文案 / 导航结构 / 测试计划时，点名后续 skill
