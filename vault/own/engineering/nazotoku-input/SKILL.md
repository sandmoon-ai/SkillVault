# 設計へのインプット（要件チェック）

设计需要齐套输入。本 skill：在动笔应用/架构设计前，核对要件侧是否「够格当输入」，缺什么标未决。

## 何时使用

- Kickoff 设计、接手续写设计书
- Review 发现追溯断裂、要件空洞
- 业务说「先设计出来再补要件」时的刹车清单

输入合格后再进 `nazotoku-app` / `nazotoku-arch`。

## 工作流

```
Input Progress:
- [ ] 1. 定系统化范围与文档来源
- [ ] 2. 业务要件
- [ ] 3. 功能要件
- [ ] 4. 数据要件
- [ ] 5. 外部連携要件
- [ ] 6. 系统状态
- [ ] 7. 非功能要件
- [ ] 8. 输出：可设计 / 带未决可部分设计 / 不可开细设
```

## 检查项

### 业务要件

- [ ] 系统化对象业务一览存在且边界清楚  
- [ ] 登場人物・役割清楚  
- [ ] 业务フロー已确认/整理  
- [ ] タスク定义清楚（フロー上的工作单元）  
- [ ] **动作场所**清楚（现场/离线/无网等会影响能否系统化与形态）  

### 功能要件

来自业务、系统应支撑的功能：

- [ ] 功能一览的 **粒度** 一致且可设计（不过粗/过碎混用）  
- [ ] 关键功能有 **事前条件 / 事后条件**  

### 数据要件

主信息种类与生命周期是设计输入（细节模型可在设计深化，但主线要有）：

- [ ] 概念模型/主实体可辨认  
- [ ] 主数据的生命周期（生成→变更→结束）有说法  

### 外部連携要件

- [ ] 外部連携一览  
- [ ] 連携方式/方向/时机的约定（含 API/文件/消息等，按项目）  

### 系统的状态遷移

必须区分的处理状态，例如「締め処理中」：

- [ ] 状态列表与含义  
- [ ] 哪些功能在哪些状态下可/不可  

### 非功能要件

功能以外：性能、可用性、安全等：

- [ ] 有书面目标或约束（即便待量化也要记未决）  
- [ ] 已知硬约束（监管、值班、窗口时间）已列出  

## 判定

| 结果 | 含义 |
|------|------|
| 可设计 | 上表关键项齐或仅有不影响骨架的小未决 |
| 带未决可部分设计 | 可做共通/边界/已清子系统；细设阻塞点列明 |
| 不可开细设 | 业务边界/主数据/关键状态缺失——先补要件 |

## 输出格式

```markdown
# 設計入力チェック

**系统**: …
**判定**: 可设计 / 带未决可部分设计 / 不可开细设

## 要件覆盖
| 域 | 状态 | 缺口 |
|----|------|------|
| 业务 | ✅/⚠/❌ | |
| 功能 | | |
| 数据 | | |
| 外部連携 | | |
| 系统状态 | | |
| 非功能 | | |

## 未决（回要件）
| ID | 内容 | 阻塞的设计 | Owner | 要否 |

## 允许开始的设计范围
- …
## 明确暂缓
- …
```

## 反模式

- 用「画面稿」冒充业务フロー已清  
- 功能一览粒度混乱仍强行详细设计  
- 忽略动作场所与系统状态，到联调才爆  
- 非功能零记载却做高可用承诺  

## 边界

- 不代替完整要件工程方法学全书  
- 发现缺口以提问清单形式回业务/BA，不擅自编造业务规则
