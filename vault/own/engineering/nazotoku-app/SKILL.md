# アプリケーション設計（入出力×機能）

本书极意：先共通与粒度，再做 **4 入出力 + 2 功能**，并做功能间整合。不先陷入程序细节。

前置：`nazotoku-input` 判定允许开设的范围。架构专项 → `nazotoku-arch`。

## 何时使用

- 写/审画面、帐票、DB、外部連携（API）规格
- オンライン/バッチ功能设计
- 功能切太碎或太糊、接口对不齐

## 工作流

```
App Design Progress:
- [ ] 1. 共通设计：边界・鸟瞰・影响应用的アーキ方針・标准
- [ ] 2. 共通要素：画面/帐票/バッチ/DB/消息
- [ ] 3. 把握复杂度（系统→功能渐进）
- [ ] 4. 明确功能粒度与功能间关系
- [ ] 5. 入出力设计 ×4
- [ ] 6. 功能设计（オンライン/バッチ）+ 处理详细
- [ ] 7. 整合：DFD / 状态↔功能
- [ ] 8. 更新未决清单
```

## 设计前：共通设计

### 全体像

- 系统边界图：范围内外  
- 鸟瞰图：主要块与关系  
- 子系统連携概要  

### 影响应用的アーキ方針（先定方向）

至少明确：

- オンライン应用方针  
- 帐票输出方针  
- ジョブ管理・执行方针  

（基建细节深挖交 `nazotoku-arch`。）

### 标准（多人时）

- 文档模板、记述粒度指南、设计标准  
- 保证可并行、可评审  

### 共通项（提高整合）

提前共同决定：

- 画面共通（布局枠、错误表现、权限提示等）  
- 帐票共通  
- バッチ共通（启停、重跑、通知）  
- DB 共通（键、审计列、软删约定等项目级）  
- 消息共通（编号、语气、国际化策略）  

## 极意：功能粒度与关系

- 先定「一个功能」的边界（对用户/对批处理有意义的单位）  
- 整理功能间：调用、前后、共享数据、互斥  
- 粒度混乱是设计债源头：过粗无法测，过碎无法懂  

复杂度：从应用到功能 **阶段性** 把握，避免一上来全细节。

## 入出力设计（4）

### 画面

- 菜单/信息架构、画面遷移  
- 各画面入出力项目、校验、权限、空/错态  
- 与功能、状态的对应  

### 帐票

- 一览与明细结构  
- 输出时机、条件、份数/送付  
- 与数据来源的对应  

### DB

- 始终意识整合性（键、参照、生命周期）  
- 与主数据生命周期、状态的一致  
- 与在线/批处理更新职责划分  

### 外部連携（含 API）

- 連携先、方向、协议/方式、频率、失败与重试  
- 数据合同（字段、码表、版本）  
- 幂等、超时、监控要点（原则级）  

## 功能设计（2）

### オンライン

- 触发、事前/事后、主流程与分支  
- 事务边界（与架构方针一致）  
- 与画面/API 的对应  

### バッチ

- 启动条件、调度、输入输出、重跑/再処理  
- 与締め状态等系统状态的关系  
- 与ジョブ方针一致  

### 处理详细

在粒度稳定后，写清算法级规则、计算、分支——仍保持可追溯到要件。

## 功能间整合

- 用数据流视角确认接口与数据是否闭环（DFD 等）  
- 用状态遷移确认「状态 × 可执行功能」无洞无矛盾

## 反模式

- 跳过共通直接每人一页一种写法  
- 先写类方法伪代码，功能边界未定  
- DB 与画面字段各写各的、无追溯  
- 外部連携只写「有接口」无失败态  
- 批处理忽略締め/重跑  

## 边界

- 具体中间件选型细节交架构 skill  
- UI 交互体验可叠 `krug-*`；实现工艺叠 `webgen-craft`
