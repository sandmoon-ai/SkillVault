# システム設計 Review（謎を解く）

审「设计」是否有共同定义、是否满足好设计条件、未决是否显性管理。先对齐语言，再挑细节。

规则来源：高安厚思『システム設計の謎を解く』（含改訂版视野）。

## 何时使用

- 基本/详细/外部/内部等词混用、范围吵架
- 设计书看起来厚，但需求对不上或互相矛盾
- 开设计前/中期体检，决定回要件还是补应用/架构

分流：要件输入 → `nazotoku-input`；入出力/功能 → `nazotoku-app`；架构/运用 → `nazotoku-arch`。

## 工作流

```
Review Progress:
- [ ] 1. 对齐本项目「设计」词汇表（工程 vs 构成要素）
- [ ] 2. 列出已有成果物与声称覆盖的设计种类
- [ ] 3. 用好设计检查表打分
- [ ] 4. 对照 4 入出力 + 2 功能 是否缺席
- [ ] 5. 共通设计/标准是否存在
- [ ] 6. 课题・未决清单是否在维护
- [ ] 7. 按严重度输出 + 下一 skill
```

## 先解两个「謎」

1. **设计一词含义散**：范围广导致每人一套说法  
2. **范围因组织/项目而模糊**：必须先书面定义「这次设计包含什么、不包含什么」  

混乱源：把 **生命周期工程上的设计**（要件后的基本/详细等）与 **系统构成要素的设计**（画面/DB/功能/架构等）横排成同级词却不定义。审查第一步做 **术语对照表**。

## 「よい設計」检查表

| 视角 | 问 |
|------|-----|
| 追溯 | 能否追到要件？孤儿设计有哪些？ |
| 网罗 | 数据/处理模式是否穷尽到约定粒度？ |
| 重复 | 名称不同、实质微妙重复的要素是否并存？ |
| 矛盾 | 要素间规则是否冲突？ |
| 运用 | 是否考虑运维/操作现实？ |
| 易懂结构 | 读者能否抓住结构？ |
| 易改 | 变更点是否局部化？ |
| 易测 | 边界与结果是否可验证？ |
| 易复用 | 共通是否抽得出？ |
| 易扩展 | 预期扩展轴是否留了缝？ |

## 设计覆盖速查（本书骨架）

**入出力设计（4）：** 画面 / 帐票 / DB / 外部連携（含 API）  
**功能设计（2）：** オンライン / バッチ  

另看：共通设计（画面/帐票/バッチ/DB/消息等）、架构、运用（改訂强调）。

缺一类且项目需要 → Critical 或 Should，取决于范围定义。

## 课题・未决

设计中必然冒出「要件该有却没有」的内容（数据单位、持有方式等）。规则：

- 记入未决清单（谁、截点、影响）  
- **不假装已决**继续细设  
- 回喂要件/业务确认

## 反模式

- 不定义范围就评「写得不够细」  
- 用文笔好坏代替追溯与矛盾检查  
- 把未决藏进含糊语句  
- 宣称敏捷所以不需要设计（本书：手法变，设计活动仍在）  

## 边界

- 不替代领域专业验收标准全文  
- UI 可用性深审可叠 `krug-*`；Web 工艺叠 `webgen-*`  
- 论证结构叠 `minto-*`
