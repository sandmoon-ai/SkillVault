# アーキテクチャと運用設計（謎を解く）

把非功能与运行现实做成可执行的架构/运用方针，并与应用设计对齐。改訂版强调运用与 API 视角。

应用入出力细设 → `nazotoku-app`。要件输入 → `nazotoku-input`。

## 何时使用

- 定层结构、事务/锁/履历、安全会话
- 性能/可用性怎么落地
- 运维：事件、变更、SLO、定型作业
- API 作为外部連携的架构约束

## 工作流

```
Arch Progress:
- [ ] 1. 系统アーキ（基建土台）要点
- [ ] 2. 应用アーキ：层、接口、实现方针
- [ ] 3. 数据整合方针（事务/锁/履历/删除/補正）
- [ ] 4. 安全・例外・日志・消息
- [ ] 5. 性能四视角 + 手段
- [ ] 6. 可用性手段
- [ ] 7. 運用设计（服务台/事件变更/SLO/作业）
- [ ] 8. 回写对应用设计的约束
```

## 系统アーキテクチャ（土台）

按需覆盖原则级决策（不必写成采购标书）：

- 服务器/算力形态、网络、存储  
- OS / 中间件职责  
- 环境区分（开发/试验/生产）与发布单元  

目标：应用设计知道「跑在什么约束上」。

## 应用アーキテクチャ

- 层结构（如表现/应用/数据，或项目选定的分层）  
- 层间接口与相互作用  
- 各层实现方针（事务归属、外部 I/O 位置、禁止跨层等）  

与 `nazotoku-app` 的在线/批处理、画面/API 边界必须一致。

## 数据整合性（常为非功能核心）

书面定方针：

| 主题 | 要定什么 |
|------|----------|
| 事务 | 边界、传播、超时 |
| 更新时机与锁 | 乐观/悲观、粒度、死锁策略 |
| マスタ履历 | 是否留史、有效期间 |
| 删除 | 物理/逻辑、级联、保留期 |
| 補正トランザクション | 如何订正已确定数据 |

## 安全

- 认证、权限、会话  
- 加密（传输/保存，按数据级）  
- 与画面/API 设计的强制点（不可仅文档愿望）  

## 例外・日志・消息

- 例外种类与处理（重试/放弃/人工）  
- 日志：格式、去向、时机、关联 ID  
- 消息管理：与共通消息设计一致  

## 性能：四个视角

| 视角 | 典型对象 |
|------|----------|
| レスポンス时间 | オンライン |
| スループット | オンライン |
| ターンアラウンド | バッチ |
| リソース效率 | 整体 |

手段原则（选用并写清取舍）：缓存、加资源、分散、体感响应改善（如异步）等——**对应哪个指标**，避免盲加。

## 可用性

- 冗长化等结构手段  
- 顺次更新等数据侧手段  
- 与 RPO/RTO 或业务可停窗口对齐（有则写，无则标未决）  

## API（改訂关注）

在外部連携架构层补充：

- 版本与兼容、幂等、限流/超时、错误模型  
- 同步 vs 异步选择理由  
- 可观测性（关联日志、指标）  

## 運用设计（改訂）

至少落到可执行条目：

- 服务台/支持入口  
- 事件・问题・变更・构成管理的职责边界（按组织裁剪）  
- 服务水平（SLO/SLA 意识）  
- 运用管理项目清单  
- 定期オペレーション vs 非定型オペレーション  

应用设计必须能被这些作业操作（重跑批、开关、权限变更等）。

## 反模式

- 抄一层「标准架构图」不对接事务与批处理  
- 性能只写「要快」无视角与测量点  
- 安全只写产品名无强制点  
- 运用零设计，上线后靠英雄主义  
- 过度设计未来百年，或完全无视已知峰值  

## 边界

- 不替代具体云厂商详细设计手册  
- 安全合规认证范围需专业评审时标明  
- 总审：`nazotoku-review`
