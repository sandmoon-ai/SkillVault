# 推敲とリライト（Step6–7）

在消息与大纲已定的前提下，把可扔草稿收成可交稿。先诊断结构与逻辑，再动词句。

前置：最好有设计令 + 完整草稿。若无消息/大纲，先 `kaku-review` → 可能退回 `kaku-design`。

## 何时使用

- 「帮我改得清楚一点」且已有成篇文字  
- 草稿完整，需要收紧、对齐读者、去掉重复  
- 结构要对齐消息，不是只改错字  

## 工作流

```
Revise Progress:
- [ ] 1. 重贴メッセージ与読み手（验收尺）
- [ ] 2. Step6 推敲：对照清单标问题（先不美化）
- [ ] 3. 判断：局部改 vs 段落级リライト vs 回设计
- [ ] 4. Step7 リライト：按优先级改结构与段落
- [ ] 5. 再推敲一遍表面层（句长、重复、语气）
- [ ] 6. 终检：三问 + 导入 + 行动是否清楚
```

## Step6 推敲（诊断）

对照设计令扫草稿：

### A. 消息对齐

- 每节是否支撑一句メッセージ？  
- 有无漂亮的聪明段落？  
- 结论是否与开头预告一致？  

### B. 读者负担

- 必给信息是否靠前、可找到？  
- 行话是否已翻译或删除？  
- 距离感/语气是否匹配读者？  
- 手机/速览场景下，小标题与首句是否可扫？  

### C. 逻辑与支撑

- 主张—论拠—数据是否断裂？  
- 有无「因此」其实推不出？  
- 【待补】是否仍假装已证实？  

### D. 构成

- 一段多意？节顺序违背读者任务？  
- 导入能否独立决定「读不读」？  
- 收束有无行动/结论？  

### E. 表面（最后看）

- 重复词、空话、超长句、指代不明  
- 可删的连接套话（「不得不说」「众所周知」）  

推敲产出应是 **问题列表 + 改法类型**，不是先涂脂粉。

## Step7 リライト（动手）

リライト ≠ 同义替换。优先层级：

| 优先级 | 动作 |
|--------|------|
| 1 | 删与消息无关的节/段 |
| 2 | 重排节顺序（读者路径） |
| 3 | 重写节内结构（先结论、一段一意） |
| 4 | 补/砍支撑，诚实标缺口 |
| 5 | 压缩句、换读者语言、调语气 |
| 6 | 错字与格式 |

若消息本身变了 → **停止リライト**，回 `kaku-design`。

### 压缩手法（服务读者，不是炫技）

- 一句一事；能砍半句就砍  
- 同一意思只保留最强一处  
- 列表承载并列，避免散文报菜名  
- 被动改主动（在适合的商务语气内）  
- 导入删欢迎词，留「为何 + 收益 + 消息」  

与 `krug-scan` 关系：Web/UI 短文可叠用「再删一半」；长商务文以消息与大纲为准，不机械删成电报。

## 分流

| 推敲发现 | 动作 |
|----------|------|
| 无消息/读者错 | `kaku-design` |
| 整节空洞且无料 | 删节或列待补，不硬写 |
| 仅拖沓重复 | 本 skill 内リライト |
| 仅错字 | 轻量校对即可 |

## 输出格式

```markdown
# 推敲メモ
**メッセージ**: …
**读者**: …

## 问题（按优先级）
1. [消息/读者/逻辑/构成/表面] …
   - 改法: 删 / 重排 / 重写段 / 补证据 / 压句

# リライト稿
…

## 变更摘要
- 删: …
- 重排: …
- 仍待补: …

## 终检
- [ ] 一句消息可指认
- [ ] 读者能行动或能下判断
- [ ] 导入值得读
- [ ] 无假装证实的待补
```

也可先给「推敲メモ」等用户确认再出力リライト稿——结构大改时优先确认。

## 反模式

- 同义词轮换假装改过  
- 加长「更正式」却不更清楚  
- 不顾设计令按个人文风重写跑题  
- 把推敲变成与同事口味争论（用消息与读者做裁判）  

## 边界

- 不篡改事实；不发明数据  
- 保留必要法律/合规表述，只改可读位置与引导  
- 全文从零构思走 `kaku-design` → `kaku-draft`；本 skill 吃已有稿  
- 版式问题转 `tsutawaru-*`；界面微文案可叠 `krug-scan`
