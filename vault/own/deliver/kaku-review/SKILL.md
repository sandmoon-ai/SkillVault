# 書くスキル Review（誰も教えてくれない書くスキル）

审文章是否「设计过再写」。目标：找出流程缺口与读者摩擦，而不是先挑文笔好坏。

规则来源：芝本秀徳『誰も教えてくれない書くスキル』。品质超不过设计——没消息、没读者、没大纲的稿，润色救不回来。

## 何时使用

- 邮件、报告、企画、说明文、简历式叙事「写了但不通」
- 用户说写不出、太散、没重点、对方看不懂
- 需要决定：重做设计 vs 只推敲

缺设计 → `kaku-design`；已有大纲要初稿 → `kaku-draft`；稿齐要打磨 → `kaku-revise`。

## 写作技能三要素（定位问题在哪层）

| 要素 | 内容 | 审稿时 |
|------|------|--------|
| 表现库存 | 词汇、修辞 | 次要；少当作主因 |
| 基本技术 | 逻辑、句、段、构成知识 | 看是否明显崩 |
| **流程** | 想法→文章的 7 Step | **优先检查** |

多数「不会写」是流程跳步，不是词不够漂亮。

## 工作流

```
Review Progress:
- [ ] 1. 定文类与交付场景
- [ ] 2. 有无一句メッセージ
- [ ] 3. 有无読み手分析
- [ ] 4. 有无构成/大纲痕迹
- [ ] 5. 导入是否决定「读不读」
- [ ] 6. 主张是否有支撑（数据・论拠）
- [ ] 7. 判断：回设计 / 重草稿 / 只推敲
- [ ] 8. 按严重度输出
```

## 检查清单

### 1. メッセージ（Step1）

- 能否用 **一句** 说出「要让读者明白/做到什么」？
- 是否在填某个 **ギャップ**（现状 → 目标之间的缺口）？
- 全文是否都在服务这句？还是主题漂移？

无消息 → Critical。先别改句子。

### 2. 読み手（Step2）

- 读者是谁？谁评价成败？
- 对方需要什么信息？缺什么会卡？
- 怎样的距离感/语气才通（简洁 / 铺垫 / 正式）？
- 是否按作者自己爽写，而非按读者任务写？

### 3. 设计先于写作

- 有无点子收集与筛选痕迹？还是想到哪写到哪？
- 有无大纲/顺序逻辑？还是靠「写着写着长出来」？
- 是否一上来就追求成稿句（常见失败）？

口诀：**品质 ≤ 设计**。设计空，则建议退回 `kaku-design`。

### 4. 导入（前書き）

- 开头几句是否回答：这是关于什么、为何现在读、读完得到什么？
- 是否用空话欢迎词烧掉耐心？
- 读者若只读导入，能否决定继续或正确归档？

### 5. 主张与支撑

寻找「数据・论拠・主张」是否成套：

- 只有主张无支撑 → 不可信
- 只有数据无主张 → 读者不知道要结论什么
- 论拠跳跃 → 连不上

### 6. 表面症状（次级）

仅在流程过关后才深究：

- 重复、冗长、一段多意
- 指代不明、被动堆砌
- 标题与正文不符

## 分流建议

| 诊断 | 下一步 |
|------|--------|
| 无消息/无读者/无大纲 | `kaku-design`（重做 Step1–4） |
| 设计有，正文乱或未写完 | `kaku-draft` |
| 消息清、结构在，表达拖 | `kaku-revise` |
| 只是错字格式 | 小修即可，不必上全流程 |

## 输出格式

```markdown
# 書くスキル Review

**文类**: …
**总判**: [流程缺口一句话]

## 核心三问
| 问 | 结果 | 现状摘要 |
|----|------|----------|
| 一句消息？ | ✅/❌ | … |
| 读者清晰？ | ✅/❌ | … |
| 设计/大纲？ | ✅/❌ | … |

## 问题清单

### 🔴 Critical（先停笔回设计）
1. **[现象]** → 缺: 消息/读者/大纲/…
   - 影响: …
   - 下一步: kaku-design / … 

### 🟡 Should fix
…

### 🟢 表面层（设计过关后再做）
…

## 建议路径
1. …
```

## 反模式

- 一上来改措辞、加形容词「显得专业」
- 用模板套话掩盖无消息
- 把读者不懂怪成「专业门槛」而不做翻译
- 建议重写全文却不指出缺口在 Step 几

## 边界

- 不审法律效力或事实真伪本身；缺支撑时标「需补证据」
- Web 扫读文案可叠 `krug-scan`；版式叠 `tsutawaru-*`
- 小说/诗歌不按本流程硬套
